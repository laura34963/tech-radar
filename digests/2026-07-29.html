Coding Agent Horror Stories: The 29 Million Secret Problem

Docker 揭露 AI coding agent 在供應鏈攻擊中洩漏憑證的風險，並以 Docker Sandboxes 隔離 secrets。

Why it matters

團隊的 rubygems 與 npm 依賴面本身就大（rails、sidekiq、nokogiri、next、axios 都有 postinstall 或原生擴充的執行時機），若在本機直接讓 agent 跑 bundle install / npm install，等於把 Rails master.key、AWS 金鑰與 kubeconfig 一起暴露在同一個檔案系統。

Recommended action

把本機 agent 的執行改到不掛載 $HOME 的容器內，並盤點目前哪些 secrets 是以純檔案形式落在開發機（config/master.key、.env、~/.kube/config）。

展開詳細

文章以實際案例說明 coding agent 在執行任務時會讀取整個開發環境，包含 ~/.aws、.env、git credentials 與 CI token；一旦 agent 拉進被投毒的套件或惡意 MCP server，這些憑證就可能被夾帶外傳。Docker 的解法是把 agent 的執行環境限縮在沙箱容器內，主機憑證不掛載進去，改以短期、範圍受限的代理憑證供 agent 使用。

Amazon EKS Provisioned Control Plane now delivers faster pod autoscaling

EKS Provisioned Control Plane 將 HPA 同步併發度提升至 Kubernetes 預設值的最多 40 倍，縮短擴容反應時間。

Why it matters

Rails/Puma 這類每個 pod 併發能力有限的服務，以及 Sidekiq 依 queue latency 觸發的擴容，最容易吃到 HPA 輪詢延遲；擴容慢幾十秒就會反映成 nginx 上游 5xx 或 job 積壓。Next.js SSR 在尖峰時的 pod 數追不上請求量，也是同一個瓶頸。

Recommended action

確認生產叢集是否已在 Provisioned Control Plane 模式，並在下次尖峰後比對 HPA 事件時間戳與 Datadog 的 pod 數／latency 曲線，重新校準目前為了補償延遲而設得過低的 target utilization 或過長的 stabilizationWindowSeconds。

展開詳細

kube-controller-manager 預設以較低的 concurrent-horizontal-pod-autoscaler-syncs 逐一輪詢 HPA 物件，當叢集內有數百個 HPA 時，單一 HPA 的重算間隔會被排隊拉長，導致實際擴容落後於流量上升。此次調整由 AWS 在託管控制平面側直接放大併發度，套用於所有 Provisioned Control Plane 叢集，使用者無需修改 HPA 資源或自行調參。

EKS 叢集的 OIDC discovery 與 JWKS endpoint 現支援 AWS PrivateLink，IRSA 驗證流程不再需要對外網路出口。

Why it matters

Why it matters

展開詳細

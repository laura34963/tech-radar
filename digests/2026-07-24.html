Runtime Enforcement, Not Runtime Advice

探討 agentic 系統應在 runtime 層做「強制執行」而非僅提供「建議」的治理主張。

Why it matters

團隊若導入 AI coding agent 或自動化 agent 存取 CI/CD 與 Kubernetes，等同引入難以預測的執行主體，需以容器隔離與 RBAC/OPA 等 runtime 政策把關其權限邊界。

Recommended action

盤點現有 agent 的工具與雲端權限，套用最小權限並在沙箱或受限 namespace 中執行。

展開詳細

文章論述隔離（isolation）、政策強制執行（policy enforcement）與受控工具存取（controlled tool access）正成為 AI agent 系統的基礎能力。核心觀點是：對 agent 的約束必須由執行環境硬性攔截，而非依賴 prompt 或模型自律。

Amazon EKS now supports EFA and placement groups on Amazon EKS Auto Mode and Karpenter

EKS Auto Mode 與 Karpenter 的 node pool 現支援 EC2 placement groups 與 EFA 網路裝置設定。

Why it matters

團隊目前的 k8s/docker 技術棧若在 EKS 上運行一般 Rails/React 服務，這項功能屬於 GPU/HPC 場景專用，對現有 web workload 幾乎無直接影響；但若未來要在既有 EKS 叢集上加入分散式 AI 訓練或推論管線，即可沿用現有 Karpenter 佈建流程而不需另建叢集。

Recommended action

若近期無 GPU 密集或分散式訓練需求，僅需記錄此能力備查；有需求時再於 NodePool 資源中評估加入 EFA 與 placement group 設定。

展開詳細

此更新讓使用者能在 EKS Auto Mode 及開源 Karpenter 的 NodePool 上，指定 EFA 網路介面設定並透過 placement groups 控制 EC2 執行個體在 AWS 實體基礎設施上的分布方式。EFA 提供作業系統繞道（OS-bypass）的低延遲、高頻寬節點間通訊，placement groups 則可依 cluster、spread 或 partition 策略調整實例的物理擺放，兩者主要服務於分散式訓練與推論等 HPC 型工作負載。
